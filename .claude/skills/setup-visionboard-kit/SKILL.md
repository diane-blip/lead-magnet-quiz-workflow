# Setup Vision Board Kit + D1

Automate Kit + D1 setup (plus generation-provider configuration) for vision board builders generated by `/lead-magnet-vision-board`. Leads and email live in the client's own Kit account; the only database is one Cloudflare D1 analytics table. See `agents/lead-magnet-agents/shared/kit-integration.md`, `agents/lead-magnet-agents/build-agent/references/cloudflare-kit-patterns.md`, and `agents/lead-magnet-agents/shared/generation-providers.md`.

## Trigger

```
/setup-visionboard-kit [business-name]
```

If no business name provided, list available vision board projects and ask which one to set up.

---

## Prerequisites

Before running this skill, the user must have:
1. The **client's own** Kit account (never SRC's/Diane's). The build agents set up custom fields, tags, and sequences in this account.
2. `wrangler` authenticated for the deploy (Cloudflare Workers + D1).
3. The following credentials ready:
   - Kit v4 API key for the **client's** Kit account (becomes the `KIT_API_KEY` Worker secret)
   - An admin password for the `/admin` analytics dashboard
   - **Only if the client opted into `live_generation`:** the client's own REST generation-provider API key (KREA/Magica), stored as the `GEN_API_KEY` Worker secret. Build-time graphics use SRC's Higgsfield account and need no client key.

## Workflow

### Step 1: Locate the Vision Board Project

1. If business name provided, construct path:
   ```
   output/[business-name]/
   ```

2. If no business name, list available projects:
   ```bash
   ls output/
   ```
   Then ask user which one to set up.

3. Find the deploy folder with package.json (handles nested structure):
   ```bash
   find [output-folder] -name "package.json" -path "*/deploy/*" | head -1
   ```
   The folder containing this package.json is where we run commands.

### Step 2: Verify Vision Board Project Exists

Check that required files exist:
- `package.json`
- `wrangler.jsonc`
- `d1/analytics-schema.sql`
- `src/pages/api/generate-graphic.ts` (vision board specific; present only when `runtime_mode = live_generation`)
- `src/pages/api/visionboard-submit.ts` (vision board specific)

If any are missing, report error and exit. Note: under the default `pregenerated_composite` mode the reveal page composites in-browser with canvas and there is no `generate-graphic.ts` runtime route.

### Step 3: Collect Credentials

Ask the user for the client's Kit credentials (and, only for live generation, the client's generation-provider key). Present this message:

```
I need the client's Kit credentials to wire up the vision board builder.
These belong to the CLIENT'S own Kit account, never SRC's.

**From the client's Kit account:**

1. **KIT_API_KEY** (Kit v4 API key, from the client's Kit account settings)
   Example: kit_abc123...
   Stored as a Worker secret. Leads and email both live in the client's Kit.

**Configuration:**

2. **ADMIN_PASSWORD** (for /admin analytics dashboard)
   Choose a secure password.
   **IMPORTANT**: Avoid special characters like `!` `$` `\` `` ` `` - they cause shell escaping issues with the wrangler CLI.
   Use alphanumeric characters and simple symbols (`-` `_` `.`) only.

**Only if this client opted into live per-user generation (runtime_mode = live_generation):**

3. **GEN_API_KEY** (the client's own REST generation-provider key, e.g. KREA or Magica)
   Stored as a Worker secret. Leave blank under the default pregenerated_composite mode —
   build-time graphics use SRC's Higgsfield account and the reveal page composites in-browser
   with canvas, so no runtime generation key is needed.

Please provide these values (you can paste them all at once or one by one):
```

### Step 4: Register Secrets and Vars

Secrets are stored with `wrangler secret put` (never in a committed file); non-secret config goes into `wrangler.jsonc` vars. From the deploy folder:

```bash
wrangler secret put KIT_API_KEY
wrangler secret put ADMIN_PASSWORD
# Only when runtime_mode = live_generation:
wrangler secret put GEN_API_KEY
```

Confirm `wrangler.jsonc` carries the non-secret vars the builder needs:
```jsonc
// vars in wrangler.jsonc
// KIT_TEMP_SEQUENCE_HOT / KIT_TEMP_SEQUENCE_WARM / KIT_TEMP_SEQUENCE_COLD  (sequence IDs from the Kit setup step)
// KIT_TAG_PREFIX
// DATA_RETENTION_ANALYTICS_DAYS   (default 90)
```

The D1 binding (`ANALYTICS_DB`) and its `database_id` also live in `wrangler.jsonc` (set in Step 6). For local development only, the same values can sit in a gitignored `.dev.vars`; production reads secrets and vars from Cloudflare.

### Step 5: Install Dependencies

```bash
cd [deploy-folder] && npm install
```

Report progress and any errors.

### Step 6: Set Up Kit (custom fields, tags, sequences)

Using the **Kit MCP** against the client's Kit account, set up the funnel per `agents/lead-magnet-agents/shared/kit-integration.md`:

1. Read `client/architecture.md` (profiles, qualification signals, selection dimensions) and `client/email-sequences.csv` + `client/content-blocks.csv`.
2. Create custom fields (`bulk_create_custom_fields`): `quiz_profile`, `quiz_temperature`, `profile_block`, `answer_callback_1`, `answer_callback_2` (vision boards use the same field shape; "temperature" is the implicit qualification signal derived from budget + timeline tags, internal only, never rendered to the subscriber).
3. Create tags: one `profile:<id>` per result profile plus `temp:hot` / `temp:warm` / `temp:cold` (prefix configurable via `KIT_TAG_PREFIX`).
4. Create the sequences (10 emails across 4 sequences for vision boards, inspiration-first) and seed each email body from `email-sequences.csv`, authoring `{{profile_block}}` / `{{answer_callback_N}}` insert points as Kit Liquid merge tags with a clean generic fallback at each point.
5. Emit the resulting sequence IDs and a `TAG_IDS` map into the deploy config (`wrangler.jsonc` vars + a generated `src/lib/kit-ids.ts`).

### Step 7: Create and Migrate the D1 Analytics Database

The only database in the adapted stack is one D1 analytics table. From the deploy folder:

```bash
wrangler d1 create [business-name]-vb-analytics    # once; paste the returned database_id into wrangler.jsonc
wrangler d1 execute ANALYTICS_DB --file=./d1/analytics-schema.sql
```

Expected output:
```
Creating analytics_events table...
  - Created analytics_events (+ indexes)
D1 analytics setup complete.
```

There are no leads / selections / email tables and no email_templates seeding — leads and all email live in the client's Kit account. The vision board's builder-flow event types (`builder_start`, `selection_made`, `email_captured`, `board_generated`, `board_downloaded`, `board_shared`, `recommendation_clicked`, `consultation_cta_clicked`) are written into the single `analytics_events` table's `event_type` column. If there are errors, report them clearly.

### Step 8: Confirm Generation Provider

Build-time graphics (one on-brand base image per result profile) are produced with **SRC's Higgsfield** account during the build, not in this setup step. Confirm the runtime mode from `workflow-config.json → generation`:

- **`pregenerated_composite` (default):** nothing to configure here. The reveal page composites the user's name + selected tags onto the matching profile base image in-browser with canvas. No runtime generation key, no API call, instant and on-brand.
- **`live_generation` (optional upgrade):** confirm the client's `GEN_API_KEY` secret is set (Step 4) and that `runtime_provider` is recorded in `workflow-config.json`. The reveal page submits a job to the client's REST provider, polls/awaits the result, and caches by a hash of selections.

If a live-generation client's `GEN_API_KEY` is missing, warn the user but do not block setup — the builder still works in composite mode using the pre-generated profile base images.

### Step 9: Verify Setup

1. Confirm the D1 `analytics_events` table was created (check command output)
2. Confirm Kit custom fields, tags, and sequences exist in the client's account
3. Confirm runtime generation mode (composite vs. live) and, if live, that `GEN_API_KEY` is set
4. Report success with next steps

### Step 10: Report Success

Output this summary:

```

## Data Model Differences from Quiz Funnel

In the adapted stack both funnels share the same plumbing — leads + email in the client's Kit account, one D1 `analytics_events` table — so the differences are in how the vision board maps onto Kit, not in separate database tables:

| Concept | Quiz Funnel | Vision Board | Where it lives now |
|---|---|---|---|
| Lead record | subscriber | subscriber | Kit subscriber |
| Qualification | explicit `quiz_score` + `temperature` | implicit signal derived from budget + timeline tags | Kit `quiz_temperature` field + `temp:` tag (internal only) |
| Profile match | `quiz_profile` | `quiz_profile` (from selected tags) | Kit `quiz_profile` field + `profile:<id>` tag |
| Selections | quiz answers → `answer_callback_N` | builder selections → `answer_callback_N` | Kit custom fields (resolved at submit time) |
| Service recommendations | product recs | service recs with `match_reason`, no price | rendered on the reveal page from `architecture.md` |
| Email sequences | 26 emails / 5 sequences | 10 emails / 4 sequences (inspiration-first) | Kit sequences |
| Generated graphic | none | per-profile base image | composited in-browser (default) or live-generated + cached (optional) — no DB table |

There is no `graphic_cache` table. Under the default composite mode there is nothing to cache; under optional live generation the Worker caches results in KV or D1 keyed by a hash of selections (see `generation-providers.md`).

### Analytics Event Types

The vision board tracks different events than the quiz:
- `builder_start` - User starts the builder
- `selection_made` - User makes a selection in a step
- `email_captured` - User provides email
- `board_generated` - Vision board graphic is generated
- `board_downloaded` - User downloads their board
- `board_shared` - User shares their board (social)
- `recommendation_clicked` - User clicks a service recommendation
- `consultation_cta_clicked` - User clicks the consultation CTA

## Error Handling

### Vision Board Project Not Found
```
Vision board project "[name]" not found.

Available projects:
- [list projects]

Usage: /setup-visionboard-kit [business-name]
```

### Missing Files
```
Missing required files in deploy folder:
- [list missing files]

This vision board may have been generated with an older version.
Please regenerate using /lead-magnet-vision-board.
```

### D1 Setup Error
```
D1 analytics setup failed.

Check the deploy:
- Is wrangler authenticated? (wrangler whoami)
- Did you run `wrangler d1 create` and paste the database_id into wrangler.jsonc?
- Does the ANALYTICS_DB binding name match wrangler.jsonc?

Error: [actual error message]
```

### Table Already Exists
```
The analytics_events table already exists in this D1 database.

The schema uses CREATE TABLE IF NOT EXISTS, so re-running is safe. To reset and recreate,
run this against the D1 database:
  wrangler d1 execute ANALYTICS_DB --command="DROP TABLE IF EXISTS analytics_events;"

Then run /setup-visionboard-kit again.
```

### Live Generation Key Missing
```
runtime_mode is set to live_generation but the client's GEN_API_KEY secret is not set.

Check:
- Did the client provide their own REST generation-provider key (KREA/Magica)?
- Run: wrangler secret put GEN_API_KEY  (from the deploy folder)

The builder still works without it in pregenerated_composite mode (the reveal page
composites onto the pre-generated profile base images in-browser), but live per-user
generation will not run until the key is set. You can add it later and redeploy.
```

## Notes

- This skill does NOT create the client's Kit account - that is part of onboarding, done first
- This skill sets up Kit (fields/tags/sequences) + the D1 analytics table; it does NOT run the final `wrangler deploy`
- Secrets live in Cloudflare via `wrangler secret put` (never committed); `.dev.vars` for local dev is gitignored
- Leads and email both live in the **client's own** Kit account, never SRC's
- Build-time graphics use SRC's Higgsfield account; runtime defaults to in-browser canvas compositing, so no runtime generation key is needed unless the client opted into `live_generation`
- Email sequences are seeded from the CSV generated by the VB Copy Agent (10 emails, 4 sequences), authored with Kit Liquid merge tags
- Record the finished deliverable in `clients/<client>/` per the vault home-base rule (not Notion)
